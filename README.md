# Avitary

**Avitary** — самостоятельный аниме-портал: собственный каталог, поиск, страницы тайтлов, личные коллекции и сообщество. Данные каталога, профилей, оценок, списков и отзывов хранятся в проекте на Supabase. Приложение не обращается к стороннему каталогу из браузера и не задерживает пользовательские запросы синхронизацией.

## Что уже реализовано

- Next.js App Router, TypeScript, Tailwind CSS; адаптивный интерфейс на русском языке с лавандовой светлой/тёмной темой и системной темой по умолчанию.
- Регистрация, вход, подтверждение и повторная отправка письма, восстановление пароля через Supabase Auth.
- Постоянный логин, редактируемое имя, публичная/закрытая карточка профиля, закрытые настройки, загрузка аватара и баннера в Supabase Storage.
- Каталог с полнотекстовым поиском, подсказками, фильтрами по жанру/году/типу/возрастному рейтингу/статусу и сортировкой с пагинацией.
- Страницы тайтлов, эпизоды и HLS-плеер; пользовательские оценки и средний рейтинг проекта.
- Личные списки «смотрю / запланировано / завершено / отложено», публичная агрегированная статистика профиля.
- Отзывы с предварительной модерацией и жалобами; административная страница доступна только роли `admin`.
- SQL-миграция с индексами, полнотекстовым поиском, узкими правами колонок и RLS; закрытые рейтинги/списки и настройки не раскрываются публичными запросами.
- Фоновая идемпотентная синхронизация каталога и эпизодов в собственную БД/Storage, запускаемая вручную или ежедневно через GitHub Actions.
- Конфигурация маршрутизации и кэширования Edgio (ранее Layer0): публичные HTML-карточки кэшируются на краю, персональные страницы и API не кэшируются.

Если Supabase-переменные не заданы, несколько страниц показывают демонстрационные карточки для локального просмотра дизайна. Это не подключённый каталог и не источник пользовательских данных; для регистрации, поиска и личных функций настройте собственный проект Supabase.

## Стек и границы интеграций

- **Веб-приложение:** Next.js 15 App Router, React 19, TypeScript, Tailwind.
- **Данные и аккаунты:** Supabase PostgreSQL, Auth и Storage. Браузер использует только URL проекта и публичный anon key; права ограничиваются RLS и грантами колонок.
- **Почта:** Resend подключается к Supabase Auth по SMTP и используется только для писем подтверждения и сброса пароля.
- **Фоновая загрузка метаданных:** `scripts/sync-aniliberty.ts` получает страницы каталога и сведения об эпизодах, затем записывает их в проектную БД и загружает постеры/баннеры в собственный bucket `anime-media`. Ошибка импорта изображения не приводит к публикации исходного URL в каталоге.
- **Стримы:** HLS-ссылки эпизодов хранятся в БД и передаются видеоплееру только на странице выбранного тайтла.
- **Пользовательский браузер не отправляет запросы к API источника метаданных.** Поиск, подсказки, профили и каталог читаются из Supabase.

## Локальный запуск

Требуется Node.js 20.11+ (рекомендуется Node 22) и npm.

```bash
npm ci
cp .env.example .env.local
```

Заполните в `.env.local`:

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://<project-ref>.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=<public-anon-key>
```

`SUPABASE_SERVICE_ROLE_KEY` нужен только скрипту фоновой синхронизации — не добавляйте его в `NEXT_PUBLIC_*`, клиентский код, публичные логи или Git. Для локальной разработки без активной синхронизации его можно не заполнять. Затем:

```bash
npm run dev
```

Откройте `http://localhost:3000`. Проверки проекта:

```bash
npm run typecheck
npm run lint
npm run build
```

## Supabase: проект и миграция

1. Создайте Supabase-проект и сохраните Project URL и публичный anon key.
2. Примените `supabase/migrations/20261001000000_initial_schema.sql` через **SQL Editor** Supabase либо подключите Supabase CLI и выполните `supabase db push`. Миграция создаёт таблицы/представление каталога, поисковую функцию, триггеры регистрации, RLS-политики и публичные buckets `profile-media` и `anime-media`.
3. В **Authentication → Providers → Email** включите регистрацию по email/паролю и подтверждение адреса. Не отключайте `Confirm email` в production.
4. В **Authentication → URL Configuration** задайте точный production Site URL и добавьте разрешённые Redirect URLs, как минимум локальный `http://localhost:3000/auth/callback` и production `https://ВАШ-ДОМЕН/auth/callback`. Добавляйте preview-домены только при необходимости; не используйте широкие wildcard-правила.
5. В настройках API скопируйте URL и публичный anon key в hosting environment. Service role key потребуется только среде фонового sync.
6. По желанию включите локальный Supabase CLI (`supabase start`) для разработки Auth/SQL. В `supabase/config.toml` замените шаблонный production-домен и адрес отправителя перед тем, как применять эту конфигурацию к реальному проекту.

### Данные и доступ

- `anime_catalog` — публичное представление с опубликованными полями тайтла и агрегатами рейтинга/популярности; идентификатор источника и исходные URL обложек в нём отсутствуют.
- Таблица `anime` выдаёт публичным ролям только необходимые колонки. `poster_source_url`, `banner_source_url` и `external_id` доступны только фоновой роли синхронизации.
- Рейтинги отдельного пользователя и его списки закрыты RLS; наружу отдаются только средние оценки и агрегированная статистика профиля.
- Настройки темы доступны только владельцу. Email хранится в Supabase Auth и не публикуется в профиле.
- Отзыв публикуется после проверки модератором. Роль администратора хранится в `app_metadata`, а не в редактируемых пользователем метаданных.
- Публичное чтение изображений идёт из Storage проекта; пользователь может загружать файлы только в собственную папку профиля.

### Администратор модерации

После регистрации найдите UUID пользователя в Supabase **Authentication → Users** и установите доверенную роль серверным Admin API. Выполняйте команду локально в закрытой среде, подставив собственные переменные; не публикуйте service role key:

```bash
SUPABASE_URL='https://<project-ref>.supabase.co' \
SUPABASE_SERVICE_ROLE_KEY='<service-role-key>' \
USER_ID='<auth-user-uuid>' node --input-type=module <<'NODE'
import { createClient } from '@supabase/supabase-js';
const admin = createClient(process.env.SUPABASE_URL, process.env.SUPABASE_SERVICE_ROLE_KEY);
const { data, error } = await admin.auth.admin.updateUserById(process.env.USER_ID, {
  app_metadata: { role: 'admin' },
});
if (error) throw error;
console.log(`Admin role assigned to ${data.user.id}`);
NODE
```

Пользователю потребуется обновить сессию, затем страница `/admin` откроет очередь модерации. Удаляйте роль тем же Admin API, заменив `app_metadata` на `{}`.

## Resend и подтверждённый домен

Resend не регистрирует пользователей и не заменяет Supabase Auth: он доставляет только транзакционные письма Supabase.

1. Добавьте и подтвердите **свой домен отправителя** в Resend.
2. В DNS у регистратора внесите SPF и DKIM-записи, которые Resend показывает именно для этого домена. Не создавайте несколько SPF TXT-записей на одном hostname: при наличии SPF объедините механизмы в одну запись. Дождитесь статуса Verified.
3. Настройте DMARC на `_dmarc.ВАШ-ДОМЕН` и сначала наблюдайте отчёты. Например, политика мониторинга может выглядеть так: `v=DMARC1; p=none; rua=mailto:dmarc@ВАШ-ДОМЕН`. Переходите к более строгой политике после проверки легитимных отправителей.
4. В **Supabase → Authentication → SMTP Settings** включите Custom SMTP и укажите `smtp.resend.com`, порт `465` (или `587` с TLS по настройкам Resend), username `resend`, password — API key Resend. Установите From address на подтверждённый адрес, например `no-reply@ВАШ-ДОМЕН`.
5. Задайте Site URL и Redirect URLs проекта (см. выше), проверьте шаблоны Confirmation и Reset Password, затем отправьте тестовые письма на реальные адреса.

Для локального Supabase CLI пароль SMTP можно передать через `SUPABASE_AUTH_SMTP_PASSWORD` из `.env.local` (шаблон есть в `.env.example`). Не добавляйте API key Resend в браузер или репозиторий. Реальные DNS-записи зависят от вашего домена и должны быть скопированы из панели Resend.

## Фоновая синхронизация каталога

Синхронизация выполняется только отдельным Node-процессом и не является частью пользовательского запроса:

```bash
SUPABASE_URL='https://<project-ref>.supabase.co' \
SUPABASE_SERVICE_ROLE_KEY='<service-role-key>' \
npm run sync:catalog
```

Скрипт проходит страницы каталога до пустой/последней страницы, повторяет временные ошибки и до четырёх запросов ведёт параллельно. Он обновляет записи идемпотентно по внешнему ID, сохраняет жанры и сведения об эпизодах, а изображения загружает в проектный bucket. В публичные записи каталога попадают только URL из собственного Storage; если загрузить изображение не удалось, публичная ссылка остаётся пустой или сохраняется предыдущая ссылка проекта.

Параметры (см. `.env.example`):

- `ANILIBERTY_API_BASE` — базовый адрес API для фонового скрипта; не задаётся в `NEXT_PUBLIC_*`.
- `SYNC_PAGE_SIZE` — размер страницы (по умолчанию 50).
- `SYNC_CONCURRENCY` — параллельная обработка (по умолчанию 4, максимум 8).
- `SYNC_INCLUDE_EPISODES` — обновлять эпизоды и HLS-ссылки (по умолчанию `true`).
- `SYNC_MAX_PAGES` — необязательный предел для короткого тестового запуска; пустое значение обрабатывает весь каталог.

### Расписание GitHub Actions

Workflow `.github/workflows/sync-catalog.yml` запускает sync ежедневно в 02:20 UTC и поддерживает ручной запуск через **Actions → Sync Avitary catalogue → Run workflow**. В настройках репозитория добавьте Actions secrets:

- `SUPABASE_URL`
- `SUPABASE_SERVICE_ROLE_KEY`

Перед первым запуском примените SQL-миграцию и убедитесь, что buckets доступны. Первый полный импорт может занять заметное время; проверяйте логи workflow и Storage usage. Секреты не требуются в настройках веб-приложения.

## Edgio / Layer0

- `edgio.config.js` — текущая конфигурация Edgio; `layer0.config.js` оставлен для совместимости со старыми командами/проектами.
- `routes.ts` — правила для публичных страниц и статических файлов. Главная, каталог и карточки тайтлов кэшируются на краю до 5 минут с stale-while-revalidate; профили (настройка видимости), приватные страницы и API не кэшируются.
- `next.config.js` подключает адаптер `@edgio/next`.

Локальная сборка/проверка интеграции:

```bash
npm run layer0:build
```

Для публикации войдите в Edgio CLI согласно настройкам вашей организации. Задайте `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_ANON_KEY` в окружении **сборки и runtime**: Next.js встраивает `NEXT_PUBLIC_*` значения во фронтенд во время build, поэтому позднейшего runtime-only значения недостаточно. Затем выполните:

```bash
npm run layer0:deploy
```

Настройте домен и DNS по инструкции Edgio. **Не** передавайте `SUPABASE_SERVICE_ROLE_KEY` в окружение веб-приложения Edgio: он нужен только GitHub Actions/закрытой sync-машине. После публикации проверьте callback-домен в настройках Supabase Auth и задайте его production Site URL.

## Страницы приложения

- `/` — главная и подборка каталога.
- `/catalog` — поиск, фильтры, сортировка и пагинация.
- `/anime/[slug]` — карточка тайтла, эпизоды, плеер, оценки и отзывы.
- `/register`, `/login`, `/auth/confirm`, `/reset-password` — регистрация и Auth-потоки.
- `/u/[username]` — публичный профиль и агрегированная статистика.
- `/library` — личные списки; доступен владельцу после входа.
- `/settings` — имя, фото профиля, тема и приватные параметры аккаунта.
- `/admin` — модерация для назначенной роли `admin`.

- [ ] Применить миграцию к целевой Supabase-БД и проверить RLS через anon/authenticated роли.
- [ ] Настроить Email confirmations, Site URL, redirect URLs и SMTP Resend.
- [ ] Подтвердить SPF/DKIM, включить и проверить DMARC для домена отправителя.
- [ ] Выполнить ручную синхронизацию, проверить карточки каталога, эпизоды и Storage.
- [ ] Добавить GitHub Actions secrets и проверить ручной workflow.
- [ ] Установить переменные веб-приложения Edgio, выполнить production deploy и проверить домен/callback.
- [ ] Протестировать регистрацию, подтверждение, повторную отправку, вход, сброс пароля, оценки, списки, отзыв, жалобу и модерацию.

Локальные проверки `typecheck`, `lint` и `build` не подтверждают доставку реальных писем, работу удалённой БД, завершение полной синхронизации или production-деплой. Эти шаги требуют ваших Supabase/Resend/Edgio-проектов и секретов. В текущем lockfile `npm audit --omit=dev` не находит уязвимостей production-зависимостей; полный аудит показывает умеренные/низкие замечания в development/build-инструментах Edgio 7 и ESLint. Не запускайте `npm audit fix --force` без повторной проверки совместимости Edgio-сборки.
